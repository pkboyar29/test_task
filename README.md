[Демо версия](https://test-task-one-puce.vercel.app/)

Запуск проекта

```bash
npm install
npm run dev
```

Какие технологические решения приняты:

- структура проекта частично приближена к FSD, общие и переиспользуемые ui компоненты вынесены в `components/common`, бизнес сущности товаров и корзины в `components/entities` и страницы в `app`
- для стилей использовал SCSS вместо CSS, потому что 1)с scss и его преимуществами знаком, 2)scss позволяет использовать переменные (вынес в переменные часто используемые цвета и брейкпоинты), также удобен при использовании методологии БЭМ благодаря вложенности
- в глобальном состоянии rtk хранятся товары из корзины и избранного. После hydration данные восстанавливаются из local storage в useEffect, когда компонент уже отрендерился на клиенте (т.е. клиентский и изначальный серверный html совпадут, и hydration mismatch не будет)
- для проверки того, находится ли товар в избранном или корзине, использованы мемоизированные селекторы `createSelector`. Благодаря этому значение не пересчитывается при каждом ре-рендере, если массивы `favorites` и `cartItems` не изменились. Также потому что эти вычисления используются в разных местах (каталог, страница избранного, страница конкретного товара), т.е. нам нужна мемоизация на уровне redux
- `useMemo` применен для мемоизации вычисления всех возможных категорий в каталоге (`categories`), чтобы при изменении фильтра/варианта сортировки/состояния redux или чего-то еще не пересчитывалось это значение. `useMemo` для filteredProducts и sortedProducts уже не используется, так как эти значения напрямую зависят от выбранных фильтров/сортировки/redux состояния, и при их изменении они в любом случае будут пересчитываться (т.е. в данном случае польза от мемоизации ограничена)
- пагинация клиентская: серверный компонент загружает одним запросом список товаров и отбирает только нужную часть массива на основе query параметра `page`. Меняя `page`, мы запрашиваем у сервера next.js новую страницу с новым url. После отбора нужной части массива фильтрация/сортировка происходят на этих данных
- для удаления товаров из корзины (в `CartItem`) использовано отложенное удаление через 3 секунды с возможностью отмены или мгновенного подтверждения удаления. `setTimeout` висит в самом компоненте, т.е. при его размонтировании удаление фактически прекратится
- для поиска (в `ProductSearch`) использован debounce паттерн для обработки поискового запроса: поиск выполняется через 500мс после последнего изменения значения
- для отображения изображений используется `next/image`. Предусмотрен fallback с текстом, если у товара нету изображения или изображение не загружается
- для загрузки списка товаров используется `fetch` с опцией `next: { revalidate: 40 }`, чтобы next.js кешировал ответ и заново делал запрос раз в 40 секунд. У нас этот запрос используется в разных местах - для запроса списка товаров, для страницы конкретного товара и его metadata. Так как в нашем случае ответ api запроса никак не меняется, можно впринципе использовать опцию `{cache: 'force-cache'}`
- динамические импорты нигде не используются, так как все импортируемые компоненты используются на страницах сразу после загрузки и имеют небольшой размер
- для SEO для каждой страницы указан объект с метаданными, где определены отдельные заголовки, описания и OG теги. На странице конкретного товара написана функция `generateMetadata`, которая динамически формирует эти метаданные
- при верстке использовались семантические html теги там где нужно и ARIA атрибуты для улучшения доступности
